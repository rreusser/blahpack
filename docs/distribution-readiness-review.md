# Distribution-Readiness Review

Date: 2026-07-02. Scope: repo hygiene (unused files), build/packaging
consistency, linter/gate relevance, and signature-mapping consistency —
with emphasis on the *mechanisms* that enforce consistency, not just
point-in-time state.

Verification environment: fresh clone, Linux, Node v22, `npm ci` from the
committed lockfile. Several findings below only reproduce on a fresh clone —
which is exactly the environment `npm publish` and new contributors get.

---

## 0. Baseline health

- `npm ci` + root import smoke test: **works**. `import('./index.js')`
  resolves 1618 named exports; `ddot` computes correctly. The deep
  `@stdlib/*/lib/index.js` ESM specifiers resolve fine.
- Full test suite: **green** — 19,233 tests, 0 failures (~130s).
- `npm run lint`: **fails instantly on a fresh machine** (see §3).
- `node bin/gate.js <module>` works scoped; `--all` is slow (spawns
  `node --check` per file across 899 modules). Deepest checks
  (workspace family) **silently SKIP** on a fresh clone because the
  reference Fortran is gitignored and there is no fetch script.

### The most important single finding

`npm test` **cannot fail.** The script is:

```
node --test ... | awk '...'
```

The pipeline's exit status is awk's (always 0). Verified empirically: a
(deliberately broken) run with **1,278 failing tests exited 0**, and
`bin/test-failures.sh` (which does `OUTPUT=$(npm test); EXIT=$?`)
inherits the lie. The suite happens to be green today, but every green
checkmark derived from `npm test`'s exit code — including
`npm run check` — is unreliable. Fix: `set -o pipefail` in the npm
script shell (`bash -o pipefail -c '...'`) or have awk `exit` with a
nonzero code when it sees `fail [1-9]`.

## 2. Build & packaging

**P0 — tarball bloat.** `npm pack --dry-run`: **22,059 files, 6.6MB
packed / 49.4MB unpacked.** Over 12,000 of those files are per-module
`test/fixtures/*.json`, `benchmark/`, `docs/`, and `examples/` pulled in
because `files: ["lib/"]` whitelists the whole tree and npm ignores
`.npmignore` patterns for paths inside an explicit `files` entry only
inconsistently (the `lib/**/test/` globs demonstrably do not take
effect). Fix in `gen-exports.js` (which writes the `files` field): ship
only `lib/**/lib/**` + per-module `README.md`, and verify with
`npm pack --dry-run` in CI. Target is single-digit MB and ~2k files.

**P0 — license is stated three different ways.**
- `package.json`: `"license": "ISC"`
- `LICENSE.txt`: MIT text (README also says MIT)
- Module headers: `@license Apache-2.0` — and only in **423 of 899**
  modules; 476 have no header at all.

Pick one (MIT per README/LICENSE.txt seems intended), align package.json
and headers, and preserve the upstream BLAS/LAPACK BSD-3-Clause
attribution (the headers' "Derived from the BLAS 3.12.0 reference
implementation" line is good — it just needs to be everywhere and under
the right license id).

**P0 — identity metadata.** Name is `@rreusser/blapack` (hardcoded in
`gen-exports.js:93`) while the repo, Pages base URL, and README all say
**blahpack**. Description, keywords, author, and `repository` fields are
empty/absent, at `version: 1.0.0`. Decide the name before first publish —
it's permanent.

**Consistency machinery (the actual lever):** `bin/gen-exports.js` is a
proper single source of truth — it scans `lib/`, and writes `exports`,
`files`, `dependencies`, and `index.js` in one pass. Verified consistent
today (899 modules ↔ 900 exports ↔ 899 barrel lines). But **nothing runs
it**: no CI, no gate check, no pre-publish hook. The mechanism exists;
the enforcement doesn't. Add a CI step: `node bin/gen-exports.js && git
diff --exit-code package.json index.js`.

**CI enforces almost nothing.** `.github/workflows/` contains only
`deploy.yml` (Pages: bundle notebooks → vite build). No test run, no
lint, no gate, no pack smoke test. Combined with the `npm test` exit-code
bug, there is currently **no mechanism anywhere** that can turn red when
the code regresses. This is the single highest-leverage fix in the repo:
a CI workflow running (1) `npm test` (with pipefail fixed), (2)
`node bin/gate.js --all --fast`, (3) gen-exports drift check, (4)
`npm pack --dry-run` size/file-count budget, (5) tarball
install-and-import smoke test.

**Reference-data reproducibility.** `data/BLAS-3.12.0/` and
`data/lapack-3.12.0/` are gitignored with no fetch/bootstrap script, yet
`test/generate_fixtures.sh` and the gate's workspace-family checks
require them. On any machine but the author's, fixtures can't be
regenerated and three gate checks silently SKIP. Add
`bin/fetch-reference.sh` (curl from netlib, checksum) and have the gate
FAIL-or-warn loudly, not skip silently, when reference data is absent.
Same story for Python: `requirements.txt` pins `fparser==0.2.0` but no
Python version or venv bootstrap.

## 3. Linters & the gate

Two enforcement systems exist: the ESLint stack and the bespoke gate
(`bin/gate.js`, 14 check modules, ~50 checks).

**The ESLint stack is non-functional off the author's machine**, four
layers deep:
1. `tools/eslint/plugin.cjs:14` hardcodes
   `/Users/rreusser/gh/stdlib-js/stdlib` and on failure **silently**
   falls back to zero stdlib rules (~122 of ~130 rules vanish without
   an error).
2. `.eslintrc.cjs` sets `sourceType: 'script'` / `ecmaVersion: 6`, but
   every lib file is ESM — guaranteed parse errors even with a working
   toolchain.
3. Scripts pass `--resolve-plugins-relative-to`, removed in modern
   ESLint; legacy `.eslintrc` is also gone in v10.
4. The custom rules only run at all when both of the above are fixed.

**Exception erosion confirms it:** `gate.config.json` has 170 modules
with exceptions, and **157 of the 207 skip entries (76%) are for one
check: `lint.eslint-pass`** — most citing the sourceType bug verbatim.
The exception mechanism itself is healthy (mandatory reasons, 152 unique
strings, every other check <1% excepted); it has just been used to
paper over one root-cause config bug. Fixing the config (flat config,
`sourceType: module`, vendor or submodule the stdlib rules) reclaims all
157 exceptions at once.

**Which rules matter:** the locally-authored rules are exactly the
high-value ones — `signature-conformance` (checks param expansion
`LDA → strideA1/strideA2/offsetA`, `INCX → strideX/offsetX` against
`data/routines.json`), `no-dprefix-conjugate-transpose`,
`z-prefix-reinterpret`, `no-stub-wrappers`, `no-todo-params`,
`vars-order`. But `signature-conformance` is set to **`warn`** — promote
to `error` once lint runs again. The cosmetic layer (`max-len` at 80
with every ignore option enabled, quotes, semi, ~50 jsdoc-markdown
rules) is noise for translated numeric code; the gate's own
disable-whitelist already admits this. Recommendation: keep the stdlib
style layer only if stdlib upstreaming is a real goal; otherwise cut
the cosmetic rules and keep programmer-errors + the custom rules.

`prettier` is a dead devDependency: no config, no script references it.
Remove it (or adopt it and delete the ESLint style layer — one, not both).

**The gate is the real asset.** It enforces file structure (13 required
files incl. `ndarray.js` + both test files), scaffolding remnants,
string-arg validator mapping (`uplo` → `is-matrix-triangle` etc. — and
indeed 0 modules hand-roll string validation), validation-layer
placement (base.js must NOT validate; FAIL if `ndarray.js` takes an
`order` param — this is what keeps BLIS strides in the kernel tier),
workspace conventions, and complex-number reinterpret rules. Known
weaknesses:
- Not wired to CI (see §2).
- `conventions.js`'s param extractor keys on `module.exports =` but the
  code is ESM `export default` — the `ndarray-matches-base-sig` check
  runs on a fallback path and is WARN-only. Fix the extractor, promote
  to FAIL.
- Workspace-family checks SKIP silently without the gitignored Fortran
  reference data.
- Nothing forbids `ld*` params in the stride tier, which is how the
  §4 deviations slipped through.

## 4. Signature-mapping consistency

**The scheme is real, documented, and ~99% uniform.** Three tiers per
module: `base.js` (raw kernel, BLIS-style `strideA1, strideA2, offsetA`,
no validation), `ndarray.js` (public `.ndarray`, same BLIS params +
validation), `<routine>.js` (BLAS-compat `order` + `LDA` surface that
converts and delegates). Character args map to long-form strings
(`'upper'`, `'no-transpose'`, `'conjugate-transpose'`, `'unit'`),
validated by shared `@stdlib/blas/base/assert/is-*` predicates in all
899 modules. LAPACK `INFO` is uniformly consumed and returned as the
integer return value (545 LAPACK ndarray files; 0 routines throw on
numerical failure). Offsets always immediately follow their strides.
Internal call sites (e.g. `dpotrf` → `dpotf2`/`dgemm`) thread
`offsetA + j*sa1 + j*sa2` through the `base.js` tier correctly in the
sampled modules.

**Deviations found (the complete list):**

| Module | Deviation |
|---|---|
| `lapack/base/dlahr2` | Hybrid `strideT`+`ldT`, `strideY`+`ldY` instead of two strides; JSDoc scaffold noise (`@param {integer} ldT - ldT`). |
| `lapack/base/dtrttf`, `ztfttr`, `ztrttf` | Redundant leftover `lda` param alongside `strideA1, strideA2, offsetA`. |
| `lapack/base/dlamch` | No ndarray/main tier, raw single-char keys — documented, intentional exception in `gate.config.json`. Fine. |

Four modules out of 899 is an excellent conformance rate — but all four
slipped through because no check forbids leading-dimension params in the
stride tier. Add to `conventions.js`: FAIL on any `base.js`/`ndarray.js`
param matching `/^ld[A-Z]/`. Fix the four modules (breaking change to
their signatures — do it before publish, not after).

**Turning the generator into a validator:** `bin/signature.py` generates
the canonical BLIS-style signature from the Fortran; nothing ever diffs
committed code against it. A gate check that regenerates the expected
param list and compares against the committed `ndarray.js` JSDoc/params
would convert signature consistency from convention-by-review into a
mechanical invariant — this plus the `ld*` rule closes the gap that let
dlahr2 through.
